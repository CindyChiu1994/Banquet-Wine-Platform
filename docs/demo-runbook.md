# 宴遇：本機展示手冊

本作品為課程展示，所有帳號、合作餐廳、酒商、付款與分潤比例均為示範資料，不進行真實交易。依本次已確認設計使用 React、TypeScript strict、Vite、原生 CSS、npm 與 localStorage；不啟動後端或資料庫。

## 啟動與建置

在專案根目錄使用 Node.js 24 與 npm：

```powershell
npm.cmd ci
npm.cmd run dev
```

開發網址為 `http://127.0.0.1:5173`。正式驗收使用下列建置預覽：

```powershell
npm.cmd run test -- --run
npm.cmd run build
npm.cmd run preview
```

預覽網址為 `http://127.0.0.1:4173`；採嚴格固定連接埠，若已被占用請停止原有服務或確認使用者是否允許更換。以 Ctrl+C 停止自己啟動的服務。

## 身分、操作與資料保存

頁首有宴客主人、平台管理者、酒商甲、酒商乙、合作餐廳五個身分按鈕，對應四種角色。各身分使用同一筆服務資料，沒有真實登入。正常操作及身分切換保存成功後才更新畫面；失敗維持上一個已保存狀態並顯示重試提示。

資料以 `banquet-wine-demo:v1` 存在同一瀏覽器、同一網站來源。開發與預覽是不同來源，資料不互通；也不保證跨裝置、不同瀏覽器或多分頁同步。損壞或版本不符時顯示恢復提示，不自動覆寫。重設只替換本應用 key，其他儲存資料保留。

右欄「展示工具」四個入口均需先確認取代資料：空白需求、正常起點、餐廳取消前、餐廳驗齡前。正常起點預填需求但未付款，提案草稿需各酒商自行套用與送出。異常入口使用相同領域轉換規則建立完整前置紀錄。宴客預設日期為載入當日後七天，時區 Asia/Taipei。

## 填寫宴客需求

新需求至少須提前三個日曆日。系統以裝置時鐘取得現在時刻，再依 Asia/Taipei 計算當日日期；例如台北 2026/11/08 操作，最早可填 2026/11/11 00:00，包含該時間。日曆日包含週末及假日，不另要求滿 72 小時；裝置設定為其他時區仍以台北日期為準，展示前請確認裝置時鐘正確。

「宴客日期與時間」會顯示準備期及最早日期，選擇器也有下限。表單跨午夜後，送出時會以新日期重新檢查；若日期太早，錯誤會指出新的最早時間，原填寫內容保留，修正後可重試。預填日期維持台北當日後七天 18:00。

「菜色或料理類型」支援多行文字，可按 Enter 分別填寫前菜、主菜與甜點；Enter 只換行，完成後請按「提交宴客需求」。長文字會自動折行；送出後各角色的料理摘要及重新整理均保留文字與換行。僅空白或換行不能提交。

三天限制只適用於新建需求。已保存的訂單即使日期接近、已過，或由舊版建立而未符合新門檻，仍可在同一來源還原並接續原流程，不會因此被當作損壞資料或自動取消。保存格式與應用 key 不變，不需要清除既有資料。

本次輸入修正的規格、流程圖與驗收見 [improve-banquet-request-inputs](../openspec/changes/improve-banquet-request-inputs/proposal.md) 及 [E2E 清單](../openspec/changes/improve-banquet-request-inputs/e2e-testing.md)；清單僅在實測通過後標記，原封存版驗收紀錄保留。

## 正常流程角色順序

主人填六項需求並提交 → 主人確認模擬支付平台服務費 → 平台邀請兩家酒商 → 酒商甲、乙各自編輯或套用示範草稿並送出 → 主人比較後選定一家 → 餐廳確認收貨時段 → 選定酒商出貨、標記送達 → 餐廳獨立確認收貨、現場驗齡 → 主人確認購買、模擬付款給酒商 → 餐廳交付 → 主人確認收取。

只有兩份有效提案到齊才能選定，選定只代表協調意向，隨後需求與兩提案鎖定。本版不支援改價、換酒商或現場議價改量。酒商送達不等於餐廳收貨；餐廳收貨不等於主人驗齡或服務完成。

甲案例：酒款 6000 元、配送 200 元、平台服務費 500 元、餐廳現場費用 300 元，估計總支出 7000 元。已付 500 元後，後續估計支出 6500 元。主人模擬付酒商 6200 元；餐廳另收 300 元僅作提示。酒商應付餐廳分潤為酒款 6000 元 × 示範 10%＝600 元，不加到主人支出。平台不收酒款佣金。

## 兩條異常

餐廳取消：載入取消前情境，餐廳展開「無法配合，服務無法繼續」，填原因並取消；切平台模擬全額退款。結果為已取消／已退款、退款 500 元、服務費淨收入 0 元、無酒款交易與分潤，不能恢復正常履約。

驗齡失敗：載入驗齡前情境，由餐廳選未通過並填原因；立即進入待退回，禁止酒款付款與交付。服務費 500 元不退，主人新增應付 0 元，退回運費由平台負擔。只有選定酒商能確認取回，結果為已退回／服務未完成。平台可在取回前或後填非負整數成本；未填顯示待登錄，不能假裝零元。兩條異常都不產生分潤，需新需求或重設才能重演正常流程。

## 八分鐘展示腳本

| 時間 | 操作與說明 |
|---|---|
| 00:00–01:00 | 說明宴客選酒與跨角色協調需求；指出模擬模式、單瀏覽器與五個示範身分 |
| 01:00–02:00 | 正常起點提交需求、服務費付款、平台邀請兩家酒商 |
| 02:00–03:00 | 兩家酒商套用並送出提案，主人比較費用並選定甲 |
| 03:00–04:00 | 餐廳確認、酒商出貨送達、餐廳收貨，重新整理核對保存 |
| 04:00–05:00 | 驗齡通過、主人購買付款、餐廳交付、主人收取；說明分潤仍待結算 |
| 05:00–06:00 | 載入取消情境，餐廳填原因、平台退款，說明淨服務費 0 元 |
| 06:00–07:00 | 載入驗齡情境、驗齡失敗、酒商取回、平台登錄成本；說明不退服務費但不向主人加收 |
| 07:00–08:00 | 說明 P0 邊界、展示費率與資料保存限制；P1 分潤支付及餐廳確認收款未提供 |
