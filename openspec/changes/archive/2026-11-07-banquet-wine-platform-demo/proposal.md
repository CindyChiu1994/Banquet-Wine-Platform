# Proposal

## Why

宴客主人需要把選酒、比較報價及餐廳收貨交付串成可理解的流程；目前專案只有市場機會與 MVP PDF，沒有可操作的產品。本次目標是由一人於 2026-11-12 前完成、2026-11-14 繳交的課程展示作品，以約八分鐘呈現平台功能，不以真實交易、商業獲利或市場驗證作為交付門檻。

## What Changes

- 建立繁體中文、桌機優先的展示平台，固定示範身分可切換宴客主人、平台管理者、兩家酒商及合作餐廳；核心操作與狀態可保存。
- 主人填寫六項宴客需求並模擬支付平台服務費；平台人工邀請兩家酒商，由酒商編輯並送出可比較的提案，主人選定一家作為協調意向。
- 串起餐廳確認收貨安排、酒商配送、餐廳收貨與現場驗齡；通過後主人現場確認購買並模擬付款給酒商，餐廳交付，主人確認收取後才完成服務。
- 必做異常一：餐廳無法配合時段且服務無法繼續，取消服務並全額模擬退還平台服務費。
- 必做異常二：已提供建議書與配送後，餐廳驗齡未通過，禁止酒款付款與交付；服務費不退、不另收費；酒商確認取回才結束退回流程，退回運費記為平台成本。
- 顯示酒商應付餐廳的示範分潤及待結算狀態；平台不收酒款佣金。酒商支付、餐廳確認收款的完整結算操作為 P1，可延後，不能阻擋 P0 交付。
- 提供從空白建立需求、載入正常示範、跳至兩種異常前置狀態及一鍵重設；示範付款、費率及資料清楚標示。
- 不納入：真實註冊驗證、多裝置同步、實際金流與自動拆帳、真實酒款交易、AI 選酒、即時庫存、物流串接、完整財務系統、分潤精算及市場成效儀表板。

## Capabilities

### New Capabilities

- `demo-workspace`: 固定角色與酒商身分切換、展示狀態保存、情境載入及重設。
- `banquet-matching`: 六項需求、服務費模擬付款、人工邀請酒商、提案編輯比較及唯一選定。
- `restaurant-fulfillment`: 收貨協調、配送及到貨確認、餐廳驗齡、現場模擬購酒付款、交付及服務完成。
- `service-exceptions`: 餐廳無法配合的取消退款、驗齡失敗的退回、終止狀態及平台退回成本。
- `restaurant-revenue-share`: 費用分流、成交後的示範餐廳分潤計算與待結算紀錄。

### Modified Capabilities

無。已查核現有 OpenSpec capability inventory，尚無主規格。

## Impact

- 專案現況：根目錄只有 OpenSpec 設定、技能檔及 `邱郁晴_宴客酒款媒合平台.pdf`，未發現應用程式、套件設定或測試。此次為全新產品規劃，沒有既有 API 相容性或資料遷移負擔。
- 預計新增前端應用、共用流程狀態、示範資料與流程驗證；技術選擇及檔案邊界見 design.md。現有 PDF 不修改，對話中已確認的決策優先於 PDF 的舊版真人試辦與交易安排。
- P0 驗收：一條正常流程、兩條異常流程、重新整理後保存、情境重設，以及八分鐘桌機展示。餐廳費用與分潤使用明確示範值，不宣稱為實際合作條件。
- 實際營運仍需另行驗證市場需求、餐廳合作、退款條款、酒品交易與金流合規；本次不建立已合法營運或已有合作的暗示。
