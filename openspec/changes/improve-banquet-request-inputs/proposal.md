# Proposal

## Why

測試發現宴客日期可選到過去或準備期不足的時間，且料理欄位無法分行描述菜單，容易造成誤填及閱讀困難。現行規格未定義最早預約日期與多行文字行為，需先補齊可驗收的契約，並避免日期限制誤傷已保存訂單。

## What Changes

- 新需求的最早宴客時間為提交當日以 Asia/Taipei 計算、加三個日曆日的 00:00，包含該時間。例如 2026/11/08 操作，可選 2026/11/11 00:00 起；採日曆日計算。
- 日期選擇提供下限與可理解的提示；提交時重新計算門檻，拒絕缺漏、無效或過早日期，保留輸入並顯示原因。
- 新建訂單的預約限制與既有訂單讀取分開；保留原保存格式，已保存訂單不因時間經過或不符合新預約門檻而被當成損壞資料。
- 「菜色或料理類型」支援自動折行與 Enter 分行；有效多行內容在保存、重新整理及各角色需求摘要中保留換行。僅空白或換行仍為無效輸入。
- 補齊日期邊界、跨日、時區、保存與多行呈現的驗收案例，移除 E2E 共用資料對固定日期的依賴。

## Capabilities

### New Capabilities

無。

### Modified Capabilities

- `banquet-matching`：擴充「六項宴客需求」的日期有效性、多行料理及拒絕提交行為。
- `demo-workspace`：擴充「成功操作跨重新整理保存」的歷史訂單相容性與換行保存，以及「明確且可操作的課程展示」的日期提示與多行可讀性。

## Impact

- `src/domain/model.ts`：區分資料有效性與建立需求時的日期門檻，提供一致的台北日曆日期計算；預填日期維持當日後七天。
- `src/app/App.tsx`、`src/style.css`：日期下限、提示與跨日更新；多行輸入及各角色共用摘要排版。
- `src/persistence/storage.ts`：檢查載入驗證維持結構及欄位有效性，不套用當日的新建限制；`schemaVersion: 1` 與既有 key 保持相容。
- `src/domain/model.test.ts`、`scripts/e2e-case.js`、`docs/demo-runbook.md`：補充單元驗證、可重複測試資料及操作說明；E2E 定義集中在本 change 的 `e2e-testing.md`。
- 本變更是現有前端 Demo 的表單增量修正，沿用目前執行與保存方式，不需要新的 API、資料庫或套件。餐廳履約、金流、分潤及角色權限不變；原封存 change 與主規格在此次規劃階段不修改。
